# tomatofarm (production)

Global tool, environment, and worktree/branch rules live in `~/.claude/CLAUDE.md`.

## Work unit

- This checkout is production and the only integration/release owner. Features are developed and validated in TomatoDev and promoted here when the user decides; promotion carries app code only, not the TomatoDev isolation overlay.
- The current user request is the source of truth. Do not resume work from historical plan, review, evidence, or next-action files.
- Implement directly by default. Write a plan only for materially ambiguous work or several independent modules.

## Ownership boundaries

- Code ownership is in `ARCHITECTURE.md`; CSS/UI ownership is in `docs/DESIGN_SYSTEM.md`.
- Root source files are authoritative. `www/` is generated by `scripts/copy-www.js` and never edited directly.
- Edit CSS only in `styles/`, `admin/admin-hig.css`, or `test-mode-v2.css`. Root `style.css` is generated by `scripts/generate-style-entry.mjs`.
- Runtime assets are declared in `runtime-assets.js`. If a cached source or asset changes, regenerate derived files and bump `sw.js` `CACHE_VERSION` in the same change.
- UI and feature modules use the `data.js` facade. Private `users/{owner}/...` paths must use the shared owner resolver/repository and fail closed when owner selection is unresolved; never create a second writable alias.
- Administrative privilege is the signed-in account (`관_리자`), never a mode, flag, or stored session value. Do not reintroduce a client-side role switch or a path that creates or password-seeds the admin account from the browser. Read `docs/reference/ACCOUNT_MODEL.md` before touching auth, login, or any `isAdmin()` gate.
- `firestore.rules` is tracked and declared in `firebase.json`. A new top-level collection needs a rule in the same change, because rules are OR-combined and the file deliberately has no permissive catch-all. Rules are never deployed by an automated job; follow `docs/reference/FIRESTORE_RULES.md`.
- Preserve existing persisted fields through domain serializers and round-trip tests. Treat `setDoc` without merge as a full overwrite.
- One interactive DOM root has one controller that owns its rendering and internal actions. Patch values in place during input gestures; rerender only for structural changes. Do not depend on an ancestor handler that an inner `stopPropagation()` can block.
- For life-zone art or NPC work, read `docs/LIFE_ZONE_ASSETS.md` before editing.

## Verification

- Run the most relevant behavioral tests first, then the applicable suite. Buttons, inputs, modals, persistence, and update flows require behavior tests; structure tests may inspect source.
- Exercise every user-facing UI change in a browser with `node scripts/dev-start.mjs` — the exact changed controls plus the affected regression surface — then stop the server. Never use `python -m http.server` for local verification.

## Release

- A clear implementation request authorizes implementation, checks, browser verification, task commit, safe integration, and one production release unless the user says local-only or no-deploy.
- Shared surfaces such as `app.js`, `data.js`, navigation, modal infrastructure, runtime assets, CSS, or `sw.js` require a grouped release and combined regression check.
- Immediately before integration and production push, fetch `origin`, verify the exact commit/file delta, and rebuild the integration if `origin/main` moved.
- Only a clean canonical `main` may run `npm.cmd run check:repository` and `git push origin main`. Push once; never force-push.
- After Pages deployment, verify the expected commit and exercise the changed production flow.
